02

Bring memories from a long-running conversation

You choose what is worth keeping. Output from another agent starts as candidates; it becomes saved memory only after your review and confirmation.

  1. Ask the original agent to organize memories

    In a regular topic, open Memory controls → Import memories from another AI. Copy the export prompt to your original agent and review its response. Rizi does not sign into that account or read your entire chat history.

  2. Bring back the specified JSON

    Paste the complete JSON, including a Markdown code fence if present, or choose a JSON file. Select Preview candidate memories. Arbitrary transcripts, platform archives and account exports are not parsed. Previewing does not save memories.

  3. Review and select

    Check each text, source quote, role, time and reference. Edit the text and type; source evidence stays read-only. Nothing is selected by default, and scope starts at this topic. Broaden it to other topics with this companion only if wanted. Review expiry for facts and experiences.

  4. Confirm and find it again

    Select the entries you want and choose Confirm selected memories. Manage them in life facts or work preferences, and open View saved import sources to read their origins. Changing the interface language does not translate source text.

Work preference
How you want work done, such as conclusions before details.
Life fact
A current circumstance, such as your present working schedule.
Past experience
An event described by the source, not something this companion necessarily experienced.

Use assistant for an agent summary, and user only for an actual user quote. Without a reliable quote, use unknown and null; never invent evidence or dates. References remain text and are not opened or downloaded automatically.

Practice with one fictional preference

This is Rizi’s candidate-package format, not an industry standard. The example is entirely fictional. Use it to explore preview and confirmation without treating it as your own real preference.

For export-tool and Mod authors

type accepts work-preference, life-fact or life-experience. role accepts user, assistant or unknown; only unknown permits a null quote. at is a Unix timestamp in milliseconds or null; reference is descriptive text or null. Keep source.id and entry IDs stable when exporting again. Limits: 200 entries, 256 KiB UTF-8, and 300 characters per memory text.

Some entries succeeded and others failed

Review each outcome. Edits for failed entries are preserved. If no confirmation receipt arrived, use Retry and check this entry to resume the original request instead of importing it again.

Importing the same source again

Entries with the same source are marked as already imported or conflicting; they do not silently overwrite existing memories. Correct an existing memory in its controls. This is not automatic semantic deduplication or contradiction detection.

Stopping use, forgetting and copies

Stopping use keeps text and history but excludes it from new requests. Forgetting requires an impact preview and confirmation; it clears traceable copies maintained by Rizi and blocks the same old source package. The original agent conversation, separate chat history, completed results and files you kept are not removed. Already-sent content cannot be recalled. Copies with altered source IDs may not be recognized.

Changing topics or moving a runtime

Changing the topic, world or identity clears unconfirmed import drafts. Existing v1 memory backups represent external-agent evidence as unknown. Full sources remain on the current instance; keep the original candidate package separately when moving between instances.

03

Choose a Mod for this task

A Mod is a selectable way of working. It turns your request into a preparation card for review, then hands the confirmed task to the existing execution flow.

  1. Check availability

    Open Extensions → Plugins. Enabling and granting permission are separate actions: enable a disabled Mod, then review and grant its required permission. Appearing in a list does not make a Mod executable.

  2. Choose for this request

    In the original topic, choose Prepare task, select one Mod, then prepare its card. Fill required fields such as focus or audience and review the sources and selected memories. You can also explicitly choose no Mod.

  3. Confirm, then inspect the real result

    Preparing or editing a card does not call a model. Execution after confirmation may incur your configured provider’s charges. Check the task and saved result in the original topic: accepting a request or saying “done” is not a save receipt.

An update, disabled Mod, revoked permission, or changed source, memory or identity can invalidate an old card. Check the original task receipt before preparing again; repeated submission is not a recovery strategy.

Make your own way of working

A form Mod contains a manifest and a handler. The manifest declares a stable ID, version, task.prepare hook, task/research kinds and permission. Its handler supplies bilingual titles, instructions and up to six fields without changing the user’s question, sources or memories. Check the package in an isolated development environment, then actually prepare a card.

Install only local plugins you trust: they execute code and are not a sandbox against malicious code. A form does not itself grant file, network or device access. The host owns identity, authorization, actual save receipts and history.

A memory-handoff Mod can turn approved material into a JSON candidate artifact in the same format. It still goes through preview and personal confirmation above. Permission to save an artifact is not permission to confirm a memory.

In a channel you have already paired

Channels with these commands can use /mods to list methods, then /task plugin/hook -- request as shown by the bot to prepare a task. /say request explicitly skips a Mod. Listing does not execute a task. Channel configuration and pairing are separate; do not assume WeChat supports the same commands.

04

Continue the same work on your phone

The personal server stores records and runs tasks. A browser or PWA is a way to reach it. This preview serves one owner across their own devices, rather than a multi-user hosted service.

  1. Have a runtime first

    Use the personal server provided with your invitation, or have an operator set up an authorized source candidate. Configure your own model and keep that runtime reachable. The phone page is not an independent offline executor.

  2. Pair the new device

    Open the pairing page at a trusted HTTPS address. Ask the runtime operator to generate a temporary pairing code and enter it, then return to the app. Do not share the code publicly; it can be reused during its validity window.

  3. Open the same topic

    Read saved conversations, memories and results, then continue the same work. Use Install or Add to Home Screen if your system offers it. Availability depends on the browser and OS; this is not an Android APK download.

  4. Handle offline or retired devices

    The offline page neither runs tasks nor retries writes in the background. After reconnecting, check the original task and receipt. Ask the runtime operator to revoke a device you no longer use; backups and migration must preserve the complete private runtime directory.

Conversations, memories, results, model configuration and device authorization live on the runtime. Your phone does not automatically gain control over that computer’s files or apps. The web interface does not cache private APIs, chats or results for offline reading. Model tasks can still send needed content to the provider you configure.

What an operator needs

An authorized source candidate requires Node.js 22.19+ and the project dependencies. Use a separate, private, empty data directory. The personal server listens only on loopback. Phone access needs a trusted HTTPS proxy or tunnel and an exact allowed origin; the computer’s localhost address will not work on a phone.

After preparing the environment and HTTPS route, use personal-server check/start for the chosen directory, pair for a code, clients to list devices, and revoke to remove access. Keep one running instance per data directory. Complete backups, authentication material and model keys must stay out of public repositories.
